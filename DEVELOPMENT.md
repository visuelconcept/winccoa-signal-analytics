# Development

This repo holds **the versioned sources** of the Signal Analytics module — the
page (`libs/`), the Python managers (`backend/python/`), the docs and the tools.
It is **not an executable workspace by itself**: the page is developed inside a
`@wincc-oa/webui-runtime` workspace (the shell), scaffolded **in place** and
kept untracked (see `.gitignore`).

## 1. Prepare the dev workspace (once, in the repo root)

The runtime shell is third-party (installed by WinCC OA):

```bash
npm install @wincc-oa/webui-runtime
npx webui-runtime-init -y
npm install --save-dev --no-audit --no-fund
npm run init:oa-data
```

Then wire this repo's sources in — a plain node script versioned under `tools/`
(nothing is added to the runtime's `package.json`: it is generated by
`webui-runtime-init`, git-ignored, and would be wiped on re-scaffold):

```bash
node tools/wire-workspace.mjs              # idempotent; --check to preview
node tools/install-page-dependencies.mjs   # idempotent; no-op here (no external deps)
```

`wire-workspace.mjs` patches the scaffold so the dev server discovers/serves/
menu-links `libs/wui-signal-analytics` (page discovery, menu fragment merge,
app-security fragment merge, tsconfig `paths` for `@visuelconcept/wui-kit`).
Re-run it after every re-scaffold. If an anchor is not found (different runtime
version), it stops with an explicit error → patch by hand.

> The page needs **no third-party npm package** beyond the runtime: `echarts`
> is satisfied by `@siemens/ix-echarts`, already a runtime dependency.

## 2. Develop the page (HMR)

All live data comes from a running WinCC OA, proxied to `BASE_URL`:

```powershell
# Windows (PowerShell)
$env:BASE_URL="https://<oa-host>:<httpsPort>"; npm start   # https://127.0.0.1:4300
```

```bash
# Linux / macOS
BASE_URL=https://<oa-host>:<httpsPort> npm start
```

Edit `libs/wui-signal-analytics/src/` → hot reload. For real analyses the OA
target must run `signal_analytics_manager.py` (and `wui-para` for datapoint
creation); without them the page runs in demonstration mode.

## 3. Develop the Python managers

No WinCC OA needed for the analysis code — everything below the `Manager` API
is plain NumPy and tested against synthetic signals:

```bash
cd backend/python
python -m pytest tests -q               # with pytest
python tests/test_signal_analytics.py   # without
python tests/test_furnace_sim.py
```

Against a real project, deploy + restart the manager (a running manager keeps
executing the code it loaded at startup):

```bash
node tools/scripts/deploy-backend.mjs --project "<project>" --only signal-analytics
# preview: … --dry-run --no-build
```

Manager logs: `<project>/log/python<num>.log`; startup line in
`<project>/log/PVSS_II.log`.

## 4. Build & deploy the page

```powershell
$env:OUT_DIR="<project>/data/dashboard-wc"; npm run build:pages
```

⚠️ **Build on the target's runtime workspace version**: a page bundle is coupled
to the shell's import map. The menu entry is merged into the deployed
`menuconfig.json` automatically (`pageMenuMergePlugin` reads
`libs/wui-signal-analytics/menu.fragment.jsonc`).

## Screenshots

`node tools/screenshot-pages.mjs` drives the dev server with Playwright and
writes one PNG per page to `docs/images/manual/` (credentials via `WUI_USER` /
`WUI_PASS` / `BASE_URL` env vars — never hardcode).

## Layout

```
libs/wui-signal-analytics/   the page (see docs/wui-signal-analytics/README.md#contents)
libs/wui-kit/                shared kit the page imports (no src/kit.ts → not a page)
backend/python/              the two managers + their packages + tests
docs/wui-signal-analytics/   module docs (README, INTEGRATION, NOTES)
docs/knowledge/project/      the Python-manager guide (versioned; the rest of
                             docs/knowledge/ is runtime scaffold, ignored)
tools/                       wire-workspace, dev-wiring/, deploy-backend, specs.json
```
